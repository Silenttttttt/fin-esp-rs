# LG air conditioner over IR: complete reference

Fin-ESP controls Muni's LG Dual Inverter split AC (Brazil, remote **AKB30086214**) over infrared.
Fin-ESP is the AC's **only** controller: the LG remote stays in a drawer. This file is the single
reference for the protocol, every known code, what was tested on this unit, and how it is wired
into Fin-ESP. Code: `src/ac.rs` (firmware), `src/web.rs` (HTTP + dashboard card),
`../fin-esp-mcp/index.mjs` (MCP server). Capture tooling: `esp32-tests/ir_receiver_test/ac_capture/`.

## Hardware

| Part | Pins | Notes |
|---|---|---|
| IR LED, KY-005 | S -> GPIO2 (D2), and GPIO4 also jumpered onto the same S pin; - -> GND | KY-005 has **no driver transistor and no series resistor**: its middle (VCC) pin is not connected. The LED only gets what the GPIO pins source, so firmware sets drive strength to max (cap 3) and drives GPIO2, GPIO4 and GPIO25 with the identical RMT signal (GPIO matrix) so jumpered pins add current. |
| IR receiver, KY-022 | S -> GPIO32, middle -> 3V3, - -> GND | Used for capture/sniffing and loopback; the NEC remote reader ignores it while Fin-ESP transmits (`ac::tx_blanking`). |

GPIO2 is a strapping pin but safe here: the LED pulls it LOW (the receiver on GPIO2 broke boot
because it drives HIGH). The onboard blue LED shares GPIO2 and flickers with each send.

**Range is the weak point.** The KY-005 is roughly 10x dimmer than the real remote, whose LED is
transistor-driven from the battery. A transistor-equipped IR module (drop-in, same pins) or the
LED placed near the AC removes that limit.

## Protocol: LG2

* 38 kHz carrier, 50% duty, generated by the RMT peripheral (hardware-timed).
* Pulse-distance: every bit is a mark followed by a short (0) or long (1) space. MSB first.
* Frame: header mark/space, 28 bits, closing mark. One frame per command, no repeats.
* 28 bits = `0x88` signature (8) + command (16) + checksum (4).
  **Checksum = sum of the four command nibbles & 0xF.**
* Settings command layout (bits of the 28-bit frame):
  `Sign:8 | Power:2 | flags:2 | Running:1 | Mode:3 | Temp:4 (C - 15) | Fan:4 | Sum:4`
  * Power: 0 on, 3 off (off frame is `0x88C0051`).
  * **Running flag (bit 15):** set on every settings change while the AC is already on, clear only
    on the frame that powers it on. Source: Arduino-IRremote `LG_SWITCH_ON_MASK`; confirmed on
    this remote (power-on `0x8800347`, change-while-on `0x88083A5`).
  * Mode: 0 cool, 1 dry, 2 fan, 3 auto (LG "AI"), 4 heat.
  * Fan nibble: 0 lowest, 1 low, 2 medium, 10 high, 4 max, 5 auto (9 = alternate low).

### Timing (calibrated to this remote, the fix that made it work)

Generic library timings (header 3200/9900, mark 480, spaces 550/1600) were 4-5% off this remote,
and with the weak LED the AC rejected every frame. Calibrated values (`ac.rs` `HDR_MARK`...):

| | TX value (us) | Real remote, measured | Fin-ESP, measured after calibration |
|---|---|---|---|
| Header mark / space | 3050 / 9450 | 3097 / 9420 | 3113 / 9399 |
| Bit mark | 460 | 495 | ~520 |
| 0 space | 540 | 504 | ~480 |
| 1 space | 1540 | 1504 | ~1480 |

Measured = through the KY-022 receiver (which shifts edges a little), same receiver for both.

## Codes

Legend: **Tested here** = sent from Fin-ESP to Muni's unit and the result observed.
Beep meaning on this unit: 1 beep = accepted; 4 beeps = not supported by this unit.

### Settings, power, presets (all absolute)

| Function | Frame | Tested here |
|---|---|---|
| Off | `0x88C0051` | yes, turns off |
| On / settings | `0x880` + mode/temp/fan + sum (power-on), `0x8808...` while running | yes |
| Jet (max cooling) | `0x8810089` | captured from remote; no "jet off" code exists, any settings frame ends it |
| Auto-clean on / off | `0x88C00B7` / `0x88C00C8` | on: 1 beep, accepted |
| Energy saving on / off | `0x8810045` / `0x8810056` | not yet (button exists on remote) |
| Power limit (Energy Ctrl) 100 / 80 / 60 / 40 % | `0x88C07F2` / `0x88C07D0` / `0x88C07E1` / `0x88C0804` | 80% captured from remote |
| Show power draw (momentary) | `0x88C0466` | yes, display showed "0.0 kW" (compressor idle) |
| Ion / plasma on / off | `0x88C000C` / `0x88C0084` | 4 beeps, **unsupported on this unit** |
| Outdoor-unit quiet on / off | `0x88C0A6C` / `0x88C0A7D` | 4 beeps, **unsupported on this unit** |
| Display light | `0x88C00A6` | not offered: toggle only |
| Diagnostic mode (tones) | `0x88C0CE6` | **never send casually** |

### Airflow

| Function | Frame | Notes |
|---|---|---|
| Up/down flap fixed positions | `0x8813048` ... `0x881309D` (commands 1304-1309) | 1304/1305/1306 captured from this remote's flap button |
| Up/down swing / stop | `0x8813149` / `0x881315A` | per IRremoteESP8266; Arduino-IRremote calls 1314/1315 "wall swing on/off" |
| Left/right swing / stop | `0x881316B` / `0x881317C` | documented for other units, untested here |
| Commands 130B-130F (`0x88130BF`, `0x88130C0`, `0x88130D1`, `0x88130E2`, `0x88130F3`) | | emitted by this remote's flap button cycle; probably fixed left/right positions (inference) |

### Timers: never sent by Fin-ESP

The AC's own timers (`0x8xxx` on, `0x9xxx` off, `0xAxxx` sleep, minutes in the low bits,
`0xB000` clear) are deliberately unused: an AC-side timer changes state without Fin-ESP knowing.
Fin-ESP runs its own timer (`ac::sleep_in`, persisted unix deadline) and sends OFF itself.
Captured from this remote: sleep 30 min `0x88A01E9`, timer on/off 60 min `0x88803C7`/`0x88903C8`,
off 120 min `0x8890788`.

### This remote's button map (captured 2026-10-26/27)

| Button | Sends |
|---|---|
| Power | `0x880...` on (full settings) / `0x88C0051` off |
| Mode | settings frame with new mode (AI `0x880B746`, dry `0x8809902`, cool `0x88083A5`) |
| Temp +/- , Fan | **36-bit** frames: a normal 28-bit settings frame + one extra byte |
| Flap | `0x8813...` positions, stepping each press |
| Jet | `0x8810089` |
| Energy Ctrl | `0x88C07D0` -> 07E1 -> 0804 -> 07F2 |
| Sleep / timer | `0xA...` / `0x8...`, `0x9...` (see above) |

### Still unknown

* **36-bit frames' extra byte** (e.g. `0x8808653` + `0xF5` or `0x6C`). Changes by 2 per degree in
  temp-button presses. No public source documents it. Fin-ESP sends plain 28-bit frames, which
  the AC accepts. Experiment: replay one with and without the byte and compare.
* **Commands `0x1408`, `0x140E`** (`0x881408D`, `0x88140E3`): from the remote, unidentified in all
  sources; sending `0x881408D` produced no visible reaction.
* Features with no IR code anywhere (likely ThinQ/wired-controller only): half-degree setpoints,
  mosquito away, humidity, filter reset, child lock, energy history.

## Fin-ESP interfaces

* Dashboard card (http://192.168.1.240): power, temp, presets (Comfort / Jet / Night / Dry),
  "turn off in", and under "More settings" mode, fan, airflow, auto-clean, energy saving, power
  limit, show power, resend.
* Blue button (GPIO27): on (cool 21C) / off.
* HTTP: `GET /ac/state`, `POST /action/ac/{on,off,set,preset,sleep,swing_v,swing_h,feature,
  show_power,resend}`; diagnostics `POST /action/ac/raw?d=...`, `GET /ac/loopback`,
  `POST /action/ac/listen?secs=N` + `GET /ac/sniff` (records the real remote).
* MCP (`fin-esp`, user scope): `fin_esp_ac_status`, `_power`, `_set`, `_preset`, `_sleep`,
  `_airflow`, `_features`, `_show_power`, `_resend`, plus the lamp/LED tools.

## Design rules (why Fin-ESP's state equals the AC's)

1. Absolute codes only, never toggles.
2. Every settings frame carries the complete state.
3. Timers run on Fin-ESP, never on the AC.
4. State persists in NVS; nothing is transmitted at boot.
5. One frame per command, no retries: reliability comes from signal quality, not repetition.

What remains outside Fin-ESP's control: a frame that physically doesn't arrive (LED power/aim),
and the AC losing mains power.
